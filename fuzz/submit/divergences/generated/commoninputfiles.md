the Go parser implements nothing for the common-input keyword: it appears only in the digest-keyword table, which prunes it. Neither does condor_submit, in any context this harness or a submit file can observe, and that is the point of this entry. `SetTransferFiles` writes `CommonInputFiles` behind two gates: a null `clusterAd`, which makes it a cluster-ad attribute, and `AllowCommonInputFiles`, which `init_base_ad` turns OFF unless it has already been told a schedd version of 25.14 or newer. A parse with no schedd attached never passes the second one. `condor_submit -dry-run` on this same build answers plainly -- "WARNING: the line 'common_input_files = a.dat, b.dat' was unused by condor_submit. Is it a typo?" -- and the oracle writes nothing for either spelling, in neither ModeAds nor ModePlacement, with one proc or three.
So there is no divergence here to close by writing the attribute: matching condor_submit for a parse with no schedd means writing nothing, which is what this parser does. Mirroring the other half -- writing the canonicalized list when the schedd IS new enough -- needs the schedd's version at ad-construction time, and nothing plumbs it there: the version is known to the CEDAR session that `Submit` opens, long after `MakeJobAd` has finished. That plumbing is the work this entry is really asking for.
Sweep cannot prove this: the generator does route the keyword to its file-list generator, so the sweep DOES submit it -- the attribute never appears on either side, which is why the entry reads "unverified" rather than reproducing. Note also that this library is older than its own source tree and knows the keyword as `common_input_files` while the tree has renamed it `transfer_common_input`; `TestDigestKeywordsMatchOracle` is the test that reports that pair, and it is the signal to rebuild rather than a Go bug.
