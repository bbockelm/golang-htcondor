the Go parser implements nothing for the common-input keyword: it appears only in the digest-keyword table, which prunes it. What C++ does with it is NOT established here. `SetTransferFiles` writes `CommonInputFiles` behind two gates -- `AllowCommonInputFiles`, which `init_base_ad` turns off unless the schedd version it was told is 25.14 or newer, and a null `clusterAd`, which makes it a cluster-ad attribute -- and against the oracle available here it writes nothing: not for `common_input_files` and not for `transfer_common_input`, in neither ModeAds nor ModePlacement, with one proc or three.
Sweep cannot prove this: the generator does route the keyword to its file-list generator, so the sweep DOES submit it -- the attribute never appears on either side, which is why the entry reads "unverified" rather than reproducing. Settling what C++ writes needs an oracle built from the same tree as the keyword table: this library knows the keyword as `common_input_files` while the source tree has renamed it `transfer_common_input`, and `TestDigestKeywordsMatchOracle` is the test that says so.
